# Deferred rules

What the rule engine deliberately does not check, and why — so "we skipped
that on purpose" is written down rather than remembered.

For what it _does_ check, see the generated [rule reference](./rules.md).

**Impact** = how much real drift the gap would catch. **Complexity** = how
hard to implement _and keep honest_ — the second half is what actually costs,
since every one of these can be built quickly and wrongly.

## The recurring failure mode, recorded

Four rules shipped or nearly shipped **broken in the same way**: a fixture
written to match its own assumption proved the check worked, while the real
codebase used a different convention.

| assumed                                     | actually                                            |
| ------------------------------------------- | --------------------------------------------------- |
| variants are `&[data-size="lg"]`            | `&.lg` — 0 vs 86 occurrences                        |
| `border: 1px solid var(--x)` binds no token | it binds one — 14% of var-using declarations        |
| a token with no CSS var was never emitted   | the token stylesheet lives outside the scanned tree |
| components are `export function X`          | 0 of 100; 55 are `const X = …; export default X`    |

Each passed its tests, and twice passed review. **Adjudicate every new rule
against a real codebase before opening the PR** — a fixture cannot catch this
class of bug by construction.
